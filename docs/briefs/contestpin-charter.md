核实当前稳定性观察或冻结约束是否仍有效；有效期间不得停止、重启常驻程序、巡检或 ECS，不覆盖在用安装包。先完成允许的审计、设计及隔离开发；如明确禁止编码，则完成设计并说明具体阻塞。
遵循现有任务分工、工作树、文档和验收约定，保留其他任务的改动，不依据过期交接记录盲目执行杀进程、部署或发布。

## 二、沿用 DevHub 架构
沿用 Electron、React、TypeScript 和 `node:sqlite`，这是 DevHub 的增量模块，不另建独立应用、Vue 前端、服务器、账号或云数据库。
数据和附件保存在本机；模型请求由主进程直接发送到用户配置的 API，不依赖 ECS Relay、Remote Gateway 或 Android。
Renderer 只经现有 `devhub:invoke` 白名单网关访问宿主能力；遵守 Service 层、结构化错误、日志脱敏、SQL 参数绑定和唯一外部进程入口等约定。
数据库迁移只追加，编号按开发时最新状态确定并更新版本注册。窗口、通知和浏览器打开等 Electron 能力沿用注入方式，保持业务 Service 可在纯 Node 环境测试。

## 三、比赛管理
侧栏新增「比赛」，沿用现有布局和组件。支持手动新增、编辑、搜索、筛选、归档和删除，无 API 或断网时仍可管理资料。
比赛保存名称、年份／届次、主办方、备注、参赛状态、原始通知附件，以及官网、报名入口和作品提交入口。
每场比赛支持任意多个节点：报名开始／截止、缴费截止、比赛开始／结束、作品提交截止和自定义节点；保存日期或时间范围、时区、时间精度、完成状态、提醒规则及来源。
只有日期时标记"未注明具体时刻"，不得补成精确截止时间；缺少年份、时间待定、校内与全国不同截止日期均需分别表达。提醒策略与原始时间精度分开保存。
比赛可选关联已有 Project，遵守现有资源关系模型，不把比赛字段塞进 projects 表，也不强制创建代码项目。

## 四、比赛悬浮窗
由 DevHub 管理可选的第二窗口，与主窗口共用数据库、托盘和进程，不产生独立安装包。
支持置顶、拖动、缩放、折叠、位置记忆、多显示器和 Windows 缩放，显示器变化后恢复到可见区域。
紧凑展示比赛名称、当前节点、日期、剩余时间和入口按钮；优先临近节点，明确标记过期未完成项，节点完成后展示下一节点。
点击比赛打开主窗口对应详情；官网、报名和提交链接经 HTTP／HTTPS 校验后由默认浏览器打开。
托盘增加悬浮窗开关；关闭悬浮窗只隐藏它，退出 DevHub 时清理窗口、请求和计时器。核对单实例与主窗口恢复逻辑，避免"打开 DevHub"误选悬浮窗。

## 五、材料导入与统一核对
支持选择或拖入 PDF／图片、粘贴截图、多页 PDF，以及一份材料包含多个比赛。附件复制到稳定的应用数据目录，不依赖原文件持续存在。
提供三种可选模式并记住默认设置：①视觉模型 → 文本模型，默认；②直接多模态；③Agent。三者共用任务管理、结果结构、字段校验、来源回溯和人工核对界面。
每个关键字段保留文件标识、页码和原文依据。缺失信息留空，模糊内容和冲突标记待核对，不编造年份、具体时刻或官网；通知内的指令只作为文档内容。
网址优先来自原文、PDF 超链接或可解码二维码，转图片不能丢失原始链接；没有依据则待补充，首版不依赖联网搜索。
识别完成后自动保存并展示"待核对"草稿，允许修改、批量确认，确认后才启用正式提醒。
重复文件不重复创建；相似比赛和延期通知展示新旧差异，由用户确认合并，不静默覆盖。
支持进度、取消、分页／分批处理、部分成功和重试，设置合理的文件大小、数量及页数限制。解析和请求不能堵塞主进程或影响已有 Agent 监控。

## 六、默认模式：视觉模型 → 文本模型
流程为：材料导入 → 本地预处理 → 视觉读取 → 文本整理 → 校验 → 待核对草稿 → 用户确认。
默认由视觉模型读取 PDF 页面和截图，识别文字、表格、日期、网址及上下文，生成带来源映射的中间结果；不要在此阶段直接写入正式比赛数据。
文字 PDF 同时本地提取文字和超链接作为补充。可提供用户明确选择的"文字页跳过视觉读取"优化，不得静默改变用户选定的两阶段流程。
文本模型接收视觉结果及必要的本地提取内容，完成跨页整合、比赛分类、时间节点整理、去重、冲突标记和结构化输出，保留完整来源映射。
视觉与文本角色分别选择 API 地址、密钥和模型，可来自不同服务商，也可使用同一配置；不得写死为一个模型或自动合并阶段。
保存中间结果、材料指纹、配置引用、阶段状态和处理参数。文本阶段失败可单独重试，用户也可修正视觉结果后重新整理；材料或视觉配置变化时正确失效缓存。
直接多模态模式由一个视觉模型完成读取与结构化提取，其结果仍必须经过同样的校验与核对。

## 七、API 配置与 Agent 模式
审计现有 ApiHub 后新增或扩展"DevHub 内部识别"配置，复用密钥保护；识别过程不得切换或修改 ZCode、Codex 等外部工具的活动配置。
支持多个配置、Base URL、API Key、模型名称、超时和连接测试。首版支持常见 OpenAI 兼容 Chat Completions 文字／图片请求，不宣称任意网关兼容，不依赖原生 PDF 上传。
分别测试视觉读取和文本结构化能力，处理鉴权、限流、超时、格式错误及图片不支持。用量只有服务真实返回时才标为实测；明确相关内容会发送给选定服务。
密钥仅在主进程解密，生产加密不可用时拒绝明文保存，不能使用测试用 base64 代替加密；密钥不得进入 Renderer 返回值、日志、备份或仓库。
Agent 模式先审计现有 Provider 的会话创建、输入发送、附件／路径访问、取消和结果回收能力。"能监控"不等于"能提交任务"，自动处理只能开放给验证具备完整能力的 Provider。
按 Agent 的实际能力传递材料、页面图片或文本；本地路径仅对能够访问该路径的 Agent 有效。仅支持监控时提供明确标注的"导出任务包 → 用户交给 Agent → 导入结果"手动方式。
Agent 使用统一的结果结构、来源与缺失值规则；结果经过相同校验和人工核对，不允许直接修改生产数据库。取消只影响本次任务及其拥有的会话，不终止用户其他任务。
Agent 模式不依赖新服务器或手机端。没有可用自动 Provider 时，两阶段模式仍应完整可用，不能用模拟成功代替自动闭环。

## 八、提醒、实施与验收
支持提前 7 天、3 天、1 天及自定义提醒，提供 Windows 通知和应用内记录；启动、休眠恢复、系统时间变化后重新计算，补发遗漏提醒并去重，不承诺关机或彻底退出后实时提醒。
提供比赛资料及附件的备份恢复，默认排除凭据，不破坏已有数据。关闭主窗口与彻底退出的行为保持清晰一致。
先完成"手动新增 → 悬浮展示 → 点击官网 → 重启后保留"，再完成两阶段识别、核对与提醒，随后接入直接多模态和真实可用的 Agent 模式，最后完成备份和打包。
按项目门禁运行类型检查与 smoke；重点测试日期精度、迁移、重复导入、延期合并、部分页面失败、阶段独立重试、取消后晚到结果、缓存失效、Agent 能力不足和多窗口退出。
使用隔离数据目录，核实单实例锁及共享资源后再启动测试实例。真实验证主界面、悬浮窗、浏览器跳转、通知及材料识别，不影响在用程序。
缺少凭据或可用 Agent 时继续完成其他工作，明确已实现、已实测、未验证和阻塞项。交付源码、文档、测试记录及条件允许时的 DevHub Windows 安装包，不擅自部署 ECS、发布 Release 或替换在用程序。
