## 1. 当前风险基线

### 1.1 安全组现状表（用户提供）

| # | 协议 | 端口 | 授权对象 | 现用途 | 风险评级 | 风险说明 |
| --- | --- | --- | --- | --- | --- | --- |
| R1 | TCP | 8746 | 0.0.0.0/0 | frps 对外服务面（`devhub-gateway` remotePort，回源家里 PC 127.0.0.1:8746） | 高 | 公网直达家庭 PC 的远程 Gateway；仅靠应用层三防线（设备 Token/防重放/限流，docs/15），传输全程明文（natpierce-setup §7.5 弱点①）；端口对全网扫描器可见，暴露面无收敛 |
| R2 | TCP | 7000 | 0.0.0.0/0 | frp 控制面（frpc 出站拨入，token 认证） | 高 | frp 协议端口全网开放；frp token 泄露 = 隧道控制面沦陷（可注入任意代理，natpierce-setup §7.5 弱点③）；控制面认证仅在登录时强制（心跳默认不重复鉴权，frp 检索证据） |
| R3 | TCP | 3389 | 0.0.0.0/0 | RDP（疑为装机默认遗留） | 高（冗余） | 公网 RDP 是爆破/凭据填充与历史漏洞的高危目标；实测外部 closed/filtered 表明「安全组放行但无监听（或被主机防火墙拦截）」——规则本身无服务对应，属纯冗余高危规则，外部探测无法区分两种状态（§1.2） |
| R4 | TCP | 22 | 0.0.0.0/0 | SSH 管理 | 高 | 全网开放的管理面；叠加部署期决策「root 密码登录保持开启」（natpierce-setup §7.2，A 级一手）= 公网密码爆破面真实存在 |
| R5 | ICMP | 全部 | 0.0.0.0/0 | ping/诊断 | 低 | 拓扑探测/主机存活枚举面；信息暴露价值大于运维价值（健康检查已有 HTTPS/WSS 心跳替代路径） |

### 1.2 主控实测佐证（2026-09-04，目标 59.110.149.11，主控提供）

| 端口 | 外部探测结果 | 与安全组现状的一致性解读 |
| --- | --- | --- |
| 8746 | **OPEN** | 与 R1 一致：frps 对外监听且安全组放行 |
| 7000 | **OPEN** | 与 R2 一致：frps 控制面监听且放行 |
| 22 | **OPEN** | 与 R4 一致：sshd 监听且放行 |
| 3389 | closed/filtered | 与 R3 不矛盾：安全组放行 + 无监听（或主机防火墙拦截）也会呈现此结果——**从外部无法区分「SG 开但无监听」与「SG 已收紧」**，故删除规则是唯一可验证的收敛动作 |
| 443 | closed/filtered | 与现状一致：安全组未放行 443（目标态需新增） |
| 80 | closed/filtered | 安全组未放行（Let's Encrypt HTTP-01 签发期才需要临时或长期放行，见 §3.3 选项一） |

> 探测数据来源为主控单点实测（2026-09-04），本文档未做任何复核探测（铁律：不执行
> 针对阿里云的操作）。

### 1.3 结论

公网面现状 = **4 个 TCP 端口全网开放 + ICMP 全放行**，其中 8746/7000 是 frp 兼容路径
的必要暴露（迁移期保留但有删除触发点，§3.1），3389 是无对应服务的纯冗余规则（立即删），
22 是全网开放的管理面（收紧授权对象 + 主机侧硬化，§2.2/§6）。

## 3. 迁移期临时规则

### 3.1 frp 路径（8746/7000）保留条件与标注

**保留前提**：原生 Relay 上线且真机验证通过之前，frp 路径是 DevHub Mobile 的唯一可用
公网链路（已实测端到端，natpierce-setup §7.4），因此 8746/7000 迁移期保留。

**临时规则标注（执行 S0 时写入规则「描述」栏，阿里云控制台支持）**：

```
MIG-TEMP devhub-frp | 来源无收敛可能（手机出口 IP 动态）| 强认证=frp token + 应用层 Token/防重放/限流（docs/15）| 删除触发点：原生 Relay 真机验收 T1+T2（见 3.2）
```

**为什么 8746 无法做来源收敛**：Android 手机经蜂窝/Wi-Fi 出口 IP 动态，源地址白名单
不可用——临时期防线只剩「强认证」一条腿（frp token 控制面 + 应用层设备 Token/防重放/
限流三防线，全部已实现并公网实测，A 级证据）。这正是必须尽快收敛到 443 单入口的理由。

### 3.2 收敛触发条件（删除 8746/7000 的里程碑门槛）

触发条件（**全部满足**后才执行 S4/S5 删除；里程碑编号以主控任务书为准，本文以 T1/T2 指代）：

- **T1 真机验收通过**：原生 Relay 在 ECS 上线，443/WSS 端到端链路于真实 Android 设备
  （或模拟器）全链路验证：health → 配对 claim → 会话/消息/事件拉取 → waiting_input
  系统通知 → reply 回流到 Agent → 断线重连 + seq 补发；
- **T2 稳定期**：T1 通过后稳定运行 ≥72h 无回退；
- **前置**：PC 侧 frpc 已停用（退出 frpc-loop 重拉器并移除 HKCU Run 键 `DevHubFRP`，
  natpierce-setup §7.3），防止删除安全组规则后 frpc 陷入无限重连噪音。

**删除顺序**：先删 8746（对外服务面，删后 frp 链路即断流）→ 观察 ≥24h → 再删 7000
（控制面）。顺序理由：8746 是实际数据入口，先断数据面可立即验证「原生 Relay 已独立
承载全部流量」；7000 保留至最后，使回滚（重加 8746 一条规则）保持一键可行。

### 3.3 迁移期 443 上线：ws:// 还是 wss://（无域名现状，三选项）

**结论先行：正式态必须是 wss://。推荐选项一（购域名 + Let's Encrypt）；域名/备案就绪
前若 Relay 先行上线，用选项二过渡；选项三仅限联调期且设时间盒，绝不承载真实数据。**

| 选项 | 内容 | 前提 | 风险 | 判定 |
| --- | --- | --- | --- | --- |
| 一：购域名 + Let's Encrypt | 域名解析到 59.110.149.11，Caddy/Nginx 以 ACME 签发并自动续期，443 反代回环 Relay | 购域名+DNS 解析；**若 ECS 位于中国大陆地域，443 对外提供 Web 服务按监管要求需完成 ICP 备案（数天至数周周期，需提前启动）**；80 端口需在签发期放行（HTTP-01），签发后可关 | 备案周期阻塞上线时间；证书自动续期依赖 Caddy/Nginx 常驻（配置不当证书过期即断链） | **推荐（正式态）**。Android 端零特殊配置（系统信任链），浏览器/curl 可直连调试，运维成本最低 |
| 二：自签证书 + Android 指纹锁定 | 自签证书上 443，Android 端以证书/SPKI 指纹锁定（OkHttp CertificatePinner 或自定义 TrustManager） | Android 端代码改动（信任锚定制）；私钥保管入凭据红线 | 信任逻辑集中到端侧，实现与测试成本高；证书轮换需 App 发版（除非预置多指纹轮换机制）；第三方工具直连调试不便 | 过渡态可接受（选项一未就绪时）。仍是 wss:// 加密，明文风险为零 |
| 三：临时 ws:// 明文 | 443 或其他端口以明文 HTTP/WS 上线 | **仅联调期 + 时间盒（建议 ≤14 天）+ 不承载真实会话内容**；禁止在明文期进行真实配对 | 凭据/会话内容公网被动可观测；**配对码可被抢先 claim**（8 位码 TTL 300s 内若被同一明文信道上的攻击者截获即可抢先完成绑定）；设备 Bearer Token 明文可被窃取并冒用至撤销 | 仅实验室联调（如本机/模拟器直连 ECS 验证 Relay 帧协议）。与 natpierce-setup §7.5 弱点①同性质且无隧道层缓解，时间盒到即切 wss |

> 与既有文档的一致性：docs/natpierce-setup.md §7.5 已预留「ECS 上 Nginx/Caddy 做 TLS
> 终结反代 127.0.0.1:8746」为升级路径；本文将其定为**正式态目标**而非可选项，并把
> frp 的 `transport.tls`（仅加密 frpc↔frps 段）明确为不满足端到端目标（App→ECS 段
> 仍明文）。

## 5. 回滚方案

### 5.1 回滚原则

- **删除式 + 存档模板**：阿里云安全组控制台不提供单条规则的「禁用/启用」开关（以控制台
  实际界面为准），因此本策略统一采用**删除式收敛**；每条删除前必须先把原规则全参数
  抄录进 §5.3 存档表，回滚 = 按存档原参数重加规则。
- **回滚窗口**：S3/S6 可随时回滚（低耦合）；S4/S5 的回滚窗口收敛于「frp 路径仍可用」
  的前提——一旦执行 S4（删 8746），frp 数据面即断，回滚重加规则后还需 frpc 在线才
  能恢复服务；因此 S4/S5 前置里包含「frpc 停用已验证、原生链路稳定 72h」，使回滚
  概率本身趋近于零。
- **S2 的特殊防锁死**：修改 22 授权对象是唯一可能「把自己锁在外面」的动作，执行前
  必须满足三重保险（§4 S2 前置）：密钥登录实测可用、`<用户管理IP>` 稳定、知悉控制台
  VNC 救援路径（不走安全组，永远可改回）。

### 5.2 逐条回滚表

| 收敛动作 | 回滚动作 | 恢复步骤 | 回滚代价 |
| --- | --- | --- | --- |
| S1（新增 443） | 删除 443 规则 | 控制台删单条 | 零风险（新增入口，删除不影响 frp 路径与其他服务） |
| S2（收紧 22） | 控制台把 22 授权对象改回 0.0.0.0/0（或新增一条放行当前所在 IP） | 经控制台 VNC/他源网络操作 | 锁死自恢复依赖控制台 VNC；改回 0.0.0.0/0 属临时排障态，排障后必须重新收紧 |

## 6. 22 端口配套主机侧整改（任务书 §五语义的落地，人工执行）

安全组（S2）只完成「限源」；「仅密钥 + 禁 root + 审计」在 ECS 主机侧 sshd 完成。
**执行顺序（防锁死）**：

1. 先配置密钥登录并**用新会话实测密钥可登**（此步先行，旧密码登录保持可用）；
2. 确认可用后，再关闭密码登录与 root 密码登录（sshd 配置：口令认证禁用、root 密码
   登录禁用——具体指令属主机操作，本文只定策略不下命令；密钥本身按凭据红线保管，
   不入仓库/文档/截图）；
3. **本节取代 docs/natpierce-setup.md §7.2 的部署期临时决策「root 密码登录保持开启」**
   ——该决策是防锁死的装机期妥协，密钥登录实测通过后即失效，natpierce-setup 文档
   相应行在后续批次修订（本 worktree 零改动，此处仅声明取代关系）；
4. 审计：SSH 登录与提权行为进入系统日志巡检范围（last/journal 常态化抽查），异常
