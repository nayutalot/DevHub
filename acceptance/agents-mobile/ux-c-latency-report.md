## 3. 三段汇总与判定

| 段 | 口径 | p50 | p95/max | 判定 |
| --- | --- | --- | --- | --- |
| 源→库 | 活跃消息 occurred_at→created_at（真库，秒粒度） | 1s | 2s | 正常 |
| 库→WS | latencyStats db-to-ws（含回填上界） | 0.54s | 0.94s | 正常 |
| 库→App 可见 | created_at→msg_visible（n=8） | 1.4s | 2.76s | 正常 |
| **源→App 可见（合计口径）** | occurred_at→msg_visible（n=4 助手回复） | **2.70s** | **4.76s** | **p95 ≤ 5s：过** |

**判定：过（公网隧道全链路，新消息出现延迟 p95 = 4.76s ≤ 5s，4/4 样本达标）。**

### 3.1 瓶颈归因（如实）

- 当前主导段 = **库→App 可见（p50 1.4s / max 2.8s）**：App 侧现状仍是 REST 轮询驱动
  （列表 2s / 详情 3s；批次 B 未实施 R5.3 的"WS 事件帧驱动 Room 失效+定向补拉"），
  可见延迟 ≈ 轮询相位 (0–3s 均匀) + 公网 RTT（~0.3–0.7s）。
- 结论：管线本身（源→库→WS）在 1.5s 内；剩余预算几乎全部消耗在轮询相位。
  若未来需要进一步压低 p95（如 ≤2s），改造点在 App 侧 WS 驱动刷新，不在服务端。

## 4. 改造前形态定性对比（docs/17 §1 事实基线）

改造前三层叠加：
1. PC 侧 `SESSIONS_REFRESH_MIN_INTERVAL_SEC=15`（全量会话刷新最快 15s 一次）+
   monitorRegistry FAST_POLL 2s / SLOW 15s 文件扫描节流；
2. App 固定轮询（2s/3s，与现同）；
3. WS 事件帧不驱动刷新（与现同）。

旧形态下"源落盘→App 可见"最坏 ≈ 15s（PC 节流相位）+ 3s（App 轮询相位）+ 隧道 RTT ≈
**18s+，p95 ≤ 5s 不可能达成**。批次 A 改造后：PC 侧活跃 provider 自适应 3s/空闲 15s +
消息尾部取数（last/prevAfter）+ db-to-ws 打点；本批实测 p95 = 4.76s，**定量通过**。
其中 App 轮询相位（0–3s）成为新主导段——与 §3.1 归因一致。

## 5. 限制与观察项（不粉饰）

1. 样本量 n=4（助手回复）/ n=8（库→App），p95 以最差样本近似；任务为无害固定短回复
   （"Reply with exactly: UX-Rn"），不代表长推理负载下的表现。
2. source-to-db 精度受 occurred_at 秒级粒度限制（±1s）。
3. **WS delivery_state 观察项**：本批全部 21 个事件 delivery_state 停留 `pending`
   （App WS 在线但服务端未标记 delivered；App 实际经 REST 轮询取数，功能无损）。
   该标记影响"WS 在线投递"审计口径与未来 WS 驱动刷新的前提，属服务端投递面问题，
   超出批次 C 越界红线（App-only），如实上报留母智能体裁决。
4. waiting_input 通知（事件→系统通知）路径本次未专项验证（属 known-limitations §5.1
   残余项 3，维持原状）。
